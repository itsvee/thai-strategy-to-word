# First-run workflow

ใช้ลำดับนี้เมื่อผู้ใช้เพิ่งติดตั้ง Skill หรือยังไม่รู้ว่าโจทย์อาจารย์ต้องการอะไร

## 1. เริ่มจากบริษัทของผู้ใช้

อ่าน `references/course-requirements.md` ก่อน ซึ่งมีคำถามแปดข้อและ feedback อาจารย์ที่ปรับให้ใช้ทุกอุตสาหกรรมไว้แล้ว ผู้ใช้ไม่ต้องส่งโจทย์ชุดเดิมใหม่

ถามสั้น ๆ:

> คุณทำงานที่บริษัทหรือหน่วยงานไหน ทำธุรกิจอะไร และรับผิดชอบส่วนใด? ถ้าเปิดชื่อไม่ได้ ใช้ชื่อสมมติได้

“รับโจทย์อาจารย์” หมายถึงอ่านสิ่งที่อาจารย์สั่งให้รายงานตอบและรูปแบบที่ต้องส่ง ไม่ใช่ให้ผู้ใช้คิดโจทย์เอง ถ้ามีคำสั่งใหม่ rubric หรือ feedback เพิ่ม รับเป็นข้อความ รูป หรือไฟล์ตามความสามารถของโฮสต์ แล้วเสริมข้อกำหนดเดิม ห้ามหยุดการสัมภาษณ์เพียงเพราะไม่มีไฟล์โจทย์

## 2. แปลงโจทย์เป็น Assignment Contract

สรุปให้ผู้ใช้เห็น:

- คำถามหรือ learning outcomes ที่ต้องตอบ
- รูปแบบเอกสารและภาษา
- กลุ่มผู้อ่าน
- ความยาวและกำหนดส่ง
- Framework ที่บังคับหรือแนะนำ
- ส่วนประกอบที่ต้องมี
- รูปแบบการอ้างอิง
- ข้อห้าม
- ไฟล์ที่ต้องส่ง

แยก `required`, `conditional`, `optional` และ `unknown` ห้ามเติมข้อกำหนดที่โจทย์ไม่ได้ระบุ

## 3. รับข้อมูลบริษัทและบทบาทงาน

ถามทีละประเด็น:

1. บริษัทหรือหน่วยงานทำธุรกิจอะไร
2. ลูกค้าหรือผู้ได้รับผลหลักคือใคร
3. ผู้ใช้ทำงานเกี่ยวข้องกับส่วนใดและมีสิทธิให้ข้อมูลระดับไหน
4. รายงานศึกษาระดับบริษัท หน่วยธุรกิจ ผลิตภัณฑ์ หรือกระบวนการใด
5. มีเอกสาร รายงาน ตัวเลข หรือข้อมูลภายในอะไรแล้ว

ถ้าผู้ใช้ไม่ต้องการเปิดชื่อจริง ใช้ชื่อสมมติหนึ่งชื่อและใช้ให้คงที่

## 4. เลือกเส้นทาง

- **Discovery:** ยังไม่มีปัญหาหรือโจทย์ธุรกิจชัด ให้ถามจากเหตุการณ์จริง
- **Revision:** มีรายงานเดิมหรือ feedback ให้ทำ issue → location → change → evidence → verification
- **Direct brief:** มีโจทย์ธุรกิจชัดแล้ว ให้ตรวจข้อมูลและเริ่ม readiness gate

ถ้าเป็นวิชาอื่น ใช้คำสั่งงานจริงแทนค่าเริ่มต้น เก็บข้อไม่ทราบไว้และถามเฉพาะส่วนที่เปลี่ยนผลลัพธ์ ระหว่างนั้นค้นข้อมูลบริษัทและสัมภาษณ์ส่วนที่ทำต่อได้

## 5. ค้นข้อมูลและรับข้อมูลภายใน

ค้นข้อมูลสาธารณะจากแหล่งปฐมภูมิก่อน พร้อมบันทึก URL วันที่ ขอบเขต และสิ่งที่แหล่งนั้นพิสูจน์

จัดข้อมูลเป็น:

- `verified`: ตรวจแหล่งแล้ว
- `user_reported`: ผู้ใช้ให้ข้อมูล พร้อมบทบาทและช่วงเวลา
- `hypothesis`: สมมติฐานที่ต้องทดสอบ
- `proposed`: ข้อเสนอหรือเป้าหมายใหม่
- `unknown`: ยังไม่มีข้อมูล

ห้ามเปลี่ยน `unknown` เป็นศูนย์หรือใช้ตัวเลขบริษัทอื่นแทน

## 6. สร้าง Coverage Plan

จับคู่ข้อกำหนดแต่ละข้อกับ:

- ส่วนในรายงาน
- หลักฐาน
- Framework
- ข้อสรุปที่ต้องเกิด
- ข้อมูลที่ยังขาด
- วิธีตรวจ

Framework ต้องตอบการตัดสินใจ ไม่ใช่มีไว้ให้ครบตาราง

## 7. ยืนยันก่อนร่าง

สรุปบริษัท ขอบเขต ปัญหา วัตถุประสงค์ ผู้อ่าน ข้อจำกัด trade-off หลักฐาน และรูปแบบ output ให้ผู้ใช้ยืนยัน

ยังไม่ร่างรายงานเต็มก่อนผ่าน `readiness_gate.py` และการยืนยันโจทย์

## 8. สร้าง output

สร้างตามลำดับ:

1. `report.html` เป็น output หลัก เปิดได้ด้วย browser
2. `coverage.html` แสดงการตอบโจทย์อาจารย์
3. `evidence.html` แสดงทะเบียนหลักฐานและข้อจำกัด
4. `feedback.html` แสดงการแก้ feedback ถ้ามี
5. สร้าง Markdown ชั่วคราวภายในเมื่อผู้ใช้ขอ Word
6. เรียก `vendor/thai-docx-upstream/scripts/thai_docx` เพื่อสร้าง `.docx`
7. เรียก `check` ตรวจ Word และส่งผลตรวจจริง

ห้ามส่ง Markdown เป็น output หลัก เว้นแต่ผู้ใช้ขอ

## 9. เกณฑ์เสร็จ

งานเสร็จเมื่อ:

- ข้อกำหนดบังคับทุกข้อมีสถานะ `covered`
- ข้อเท็จจริงทุกตัวมีหลักฐานหรือระบุว่าเป็นข้อมูลผู้ใช้
- ข้อเสนอแยกจากผลลัพธ์ที่เกิดขึ้นแล้ว
- มีข้อจำกัดและข้อมูลที่ยังขาด
- HTML เปิดได้
- Word ผ่าน build/check เมื่อผู้ใช้ขอ
- ไม่มีข้อมูลจากตัวอย่างหรือผู้ใช้อื่นหลุดเข้ารายงาน
