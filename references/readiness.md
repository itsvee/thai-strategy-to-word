# Business Readiness Gate

## สถานะการสนทนา

Discovery → Clarification → Ready for Confirmation → Confirmed Analysis → Draft → Word → Verified

การสัมภาษณ์และการตรวจเอกสารช่วยตั้งสมมติฐานได้ตั้งแต่ต้น แต่ห้ามเริ่มวิเคราะห์ฉบับสรุป ร่างรายงานเต็ม หรือสร้าง Word ก่อนผ่าน Gate และได้รับการยืนยันโจทย์ การค้นข้อเท็จจริงเพื่อปิดช่องว่างทำก่อน Gate ได้

## ข้อมูลบังคับ

`brief` ต้องมีข้อความที่มีสาระในทุกช่องต่อไปนี้:

- company: ชื่อจริงหรือชื่อสมมติที่ผู้ใช้เลือก
- business: สินค้า/บริการ วิธีสร้างรายได้หรือคุณค่าขององค์กร
- customers: ลูกค้าหรือผู้รับประโยชน์หลัก
- user_role: บทบาทผู้ให้ข้อมูลและขอบเขตอำนาจ
- strategy_scope: ระดับองค์กร หน่วยธุรกิจ หรือหน้าที่ พร้อมขอบเขต
- audience: ผู้รับรายงานและผู้ตัดสินใจ
- decision: การตัดสินใจที่ต้องการสนับสนุน
- problem: ปัญหาที่ระบุได้จากเหตุการณ์ ไม่ใช่ชื่อวิธีแก้อย่างเดียว
- desired_outcome: ผลที่อยากเห็นและทิศทางการวัด
- horizon: ช่วงเวลาที่ต้องการผล
- constraints: ข้อจำกัดที่ยืนยันแล้ว รวมกรณีผู้ใช้ยืนยันว่าไม่พบข้อจำกัดหลังตรวจสอบ
- tradeoffs: สิ่งที่ยอมแลกและเงื่อนไขที่ห้ามเสีย
- non_goals: เรื่องนอกขอบเขตที่ระบุชัด

ข้อความ “ไม่ทราบ”, “TBD” หรือข้อความว่างไม่ถือเป็นข้อมูลพร้อม ต้องกลับไปถาม ไม่ให้ผู้ช่วยเขียน “ไม่มีข้อจำกัด” แทนความไม่ทราบ

## หลักฐานและช่องว่าง

`evidence` เป็นรายการ {claim, status, source} อย่างน้อยหนึ่งรายการที่มี status เป็น verified หรือ user_reported และมี claim/source ชัดเจน verified ต้องมีหลักฐานที่ผู้ช่วยตรวจจริง user_reported ต้องระบุผู้ให้ข้อมูลเชิงบทบาทกับวันที่หรือบริบท เป็นหลักฐานการรายงานของผู้ใช้ ไม่ใช่การยืนยันอิสระ

สถานะอื่นที่อนุญาต: hypothesis, proposed, unknown ห้ามใช้ hypothesis หรือ proposed เพียงอย่างเดียวผ่าน Gate คำบอกเล่าที่เฉพาะเจาะจงของเจ้าของงานใช้เริ่มวิเคราะห์ได้โดยระบุข้อจำกัด ไม่บังคับให้ธุรกิจเล็กมีข้อมูลวิจัยเต็มก่อนเริ่ม

`gaps` แต่ละรายการต้องมี field และ treatment:

- treatment=block: เป็นช่องว่างที่ต้องถามหรือหาหลักฐานก่อน เช่น ไม่รู้ว่าปัญหาเกิดกับใคร หรือมีข้อขัดแย้งทำให้เลือกกลยุทธ์ผิด
- treatment=collection_plan: ใช้ได้กับค่าฐาน ต้นทุน หรือข้อมูลที่ยังเก็บไม่ได้ ต้องมี owner, method, deadline และ accepted=true จากคำตอบผู้ใช้

ห้ามใช้ collection_plan แทนข้อมูลบังคับใน brief ห้ามยอมรับช่องว่างกฎหมายหรือความปลอดภัยรุนแรงด้วยแผนเก็บข้อมูลเพื่อเสนอเปิดใช้งานจริง ทำได้เพียงข้อเสนอสำรวจ/ออกแบบที่มีขอบเขตปลอดภัยและไม่มีการรับรองผล

`contradictions` ต้องเป็นรายการว่างก่อนผ่าน Gate ข้อขัดแย้งแต่ละเรื่องเก็บข้อความที่ขัดกันและคำถามที่ต้องคลี่คลายไว้ ลบออกเมื่อมีหลักฐานหรือคำตัดสินที่บันทึกในสถานะแล้ว

## Revision และการยืนยัน

`brief_revision` เป็นจำนวนเต็มบวก `confirmed_revision` เป็น null หรือจำนวนเต็มบวก เมื่อไม่มี blocker และ revision ยังไม่ยืนยัน ผลคือ ready_for_confirmation เมื่อยืนยัน revision ปัจจุบันแล้ว ผลคือ ready_for_analysis หากแก้เนื้อหาสำคัญให้เพิ่ม brief_revision ทำให้การยืนยันเดิมใช้ไม่ได้

ผลลัพธ์ตัวตรวจมีสถานะเดียวและ blockers ตัวตรวจรับ JSON จากไฟล์เท่านั้น ไม่มีการเรียก API หรือเขียนข้อมูลผู้ใช้ขึ้นเครือข่าย Exit 0 ใช้เมื่อ ready_for_analysis, exit 2 เมื่อยังไม่พร้อมหรือรอยืนยัน, exit 1 เมื่ออ่านไฟล์หรือรูปแบบข้อมูลผิด

## การตรวจเชิงเนื้อหา

ตัวตรวจยืนยันเฉพาะรูปแบบและความครบถ้วน ไม่สามารถรู้ว่าคำตอบจริง น่าเชื่อถือ หรือเพียงพอหรือไม่ ผู้ช่วยต้องตรวจว่า problem ไม่ใช่เพียง “เพิ่มยอดขาย” หลักฐานสัมพันธ์กับปัญหา เป้าหมายไม่ขัดทรัพยากร และ trade-off เป็นคำตอบผู้ใช้จริง หากยังไม่ผ่านแม้ตัวตรวจให้ผ่าน ต้องกลับไปถามและห้ามเขียนรายงานต่อ
